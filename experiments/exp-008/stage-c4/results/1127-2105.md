## Proposed findings

- **FIND-099 (proposed).** For one OpenShell 0.1.9 Kubernetes-driver sandbox with its default PVC (n = 1):
  - Deleting the workload pod with a 1 s grace period ended the original Claude Code process (exit 137).
  - Within about 25 s, the replacement pod was deleted while Pending, the Sandbox CR became Suspended and the supervisor pod terminated. The actor is not identified in the evidence. The gateway phase stayed `Error` until the manual `stop`, and the workload did not recover within 120 s.
  - One native `sandbox stop` from `Error`, followed by one `sandbox start`, retained the same PVC, PV and volume handle, and started a new pod on it within 14 s.
  - The task logs and the transcript prefix were byte-identical to the reference snapshot taken while step 7 was in flight. The in-flight step was uncommitted, and its lock persisted.
  - **Limits:** one fault type (1 s-grace pod delete) on one node and one storage class (Longhorn). Node loss, PVC loss and gateway faults were not tested.
- **FIND-100 (proposed, scope limited by FIND-101).** After that restart, plain `claude --resume` on Claude Code 2.1.323:
  - started a new process that wrote into the single original transcript file, named by the original session id;
  - synthesized an interrupted-turn entry;
  - did **not** continue automatically within 186 s;
  - answered the strict codeword/LAST probe correctly, with no tool use;
  - after one `Continue the task.`, re-ran only the interrupted step 7, recovering its stale lock, with a matching token;
  - then completed steps 8–9 with no duplicate execution.

  **The run's recorded classification is `inconclusive`.** The primary-pass conclusion rests on an offline re-analysis that corrected one harness input.
- **FIND-101 (proposed; harness defect).**
  - **The defect:** `stagec4.sh:926` passes a dash-leading transcript path to `basename` without `--`, so `R_transcript_name` is empty. The C4c classifier then reports `session=new-id` whenever the project directory is `/sandbox/c/repo`, which encodes to `-sandbox-c-repo`.
  - **Why the suite missed it:** `test_metrics4.py` sets `R_transcript_name` directly, and the shell fixtures use `x/…` paths, so the shell path that computes the name was never exercised.
  - **Fix:** a one-token change (`basename --`) plus a test with a realistic path. It requires a separate reviewed PR.
  - FIND-098 remains proposed and unaffected.

## Recommendation on Phase 2

Phase 2 is **not yet warranted by the recorded evidence**. The Phase 1 question (whether native stop/start plus plain `--resume` recovers after workload loss) appears answered positively only under re-analysis.

Recommended next steps, each needing separate owner review and authorization:

1. Review and decide FIND-099 to FIND-101.
2. Review a harness-fix PR for FIND-101, with a regression test using the real transcript path shape.
3. If the owner wants a recorded rather than re-analysed classification, make one confirmatory Phase 1 run on the fixed harness.

Step 3 is optional if the owner accepts the re-analysis, since only a classifier input differs. The controller's suspend-and-supervisor-loss behaviour after workload loss (C4a) is a design input for Phase 2. It implies that controller and gateway lifecycle, not the pod fault alone, produced the `Error` and `Stopped` states. Phase 2 scope (external PVC, automatic resubmission, other fault types) should be decided after that.
