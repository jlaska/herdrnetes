## Cause (O and O-offline)

- **OpenShell's limit.** The refused element is `spec.command[3]`. The harness's `LAUNCH` argv is `/bin/sh`, `-c`, `<bootstrap>`, `<base64 of pkg.tar>`, `<pkg sha256>` (`launcher4.sh`), so index 3 is the base64-encoded task package (I; consistent with `launcher4.sh:28`, assuming the CLI prepends no element). OpenShell v0.1.9 limits each command element to 32,768 bytes, per the server's error message (O). The code location of the check was not identified (U).
- **Offline reproduction.** The package was rebuilt locally from `cb7899a` with the harness's exact `pkg_build` options. It has the same sha256 as the run (`5f524cae…`, `obs/c0-pkg.txt`) (O-offline).

  | Package | `pkg.tar` bytes | base64 element bytes | Under 32,768? |
  |---|---|---|---|
  | C4 (`stage-c4/task/launch.sh` 10,840 B + `step.sh` 6,182 B + prompt + settings) | 30,720 | **40,960** | No |
  | C0–C3 (`stage-c/task/launch.sh` 4,803 B + `step.sh` 4,840 B + prompt + settings) | 20,480 | 27,308 | Yes |

- **Why only C4 failed.** The C0–C3 package fits under the limit. That is consistent (I) with runs `1125-2153` and `1126-1017` creating their sandboxes with the same bootstrap; both recorded `pkg_bytes=20480` (O, their `c0-pkg.txt`). The C4 state-aware launcher and the token-chained `step.sh` add 7,379 bytes of scripts. With uncompressed tar block padding, that grows the archive by 10,240 bytes.
- **Why offline tests missed it.** The offline suite runs `sandbox create` against a stub CLI that does not enforce this limit. `launch4-test.sh` asserts the exact CREATE/LAUNCH argv and the byte-identical bootstrap, but not the argv element sizes. The README's risk note ("the stubs model the CLI and Kubernetes from source reading, not observation") anticipated this class of failure.

## Proposed finding

**FIND-098 (proposed).**
- **Observed.** OpenShell v0.1.9 `sandbox create` returned InvalidArgument `spec.command[3] exceeds 32768 byte limit` for a 40,960-byte argv element, the base64-inlined C4 package (O; size O-offline). The 27,308-byte element in runs `1125-2153` and `1126-1017` was accepted (O, prior runs). Within sampler coverage, no Sandbox CR, pod or PVC for the run was seen, and cleanup found no residue (O).
- **Implication (I).** If the limit is per element, inlining a task package as one base64 argv element bounds it to about 24,576 bytes before encoding. A harness that inlines a payload this way needs an offline size check on its argv elements, with margin.
- **Not shown.** Where the limit is enforced, whether it counts bytes or characters, whether it applies per element, to the whole command, or only to `spec.command`, and any limit on total argv size.

**Requirements and ADRs.** No change proposed. REQ-009 and REQ-011 stay Future. C4 produced **no** evidence on REQ-003 (state survival), REQ-006 (session continuity) or REQ-009/REQ-011, because no C4 sub-step ran. ADR-0001 is unchanged.

## Follow-up (for the owner to decide)

1. **A corrective PR (offline only).** Bring the C4 `LAUNCH` package element under the limit, with margin, without changing the bootstrap's verify-then-exec behaviour. Options:
   - Compress the package in `pkg_build` (`gzip -n`, deterministic). The bootstrap writes `pkg.tar`, checks its sha256, then runs `tar -xf`, which in GNU tar may autodetect gzip. If so, the bootstrap stays byte-identical to C0–C3 (U until tested offline in the pinned image's `tar`). The sha256 would then cover the compressed bytes.
   - Split the package across several argv elements. This changes the bootstrap.
   - Shrink the scripts. There is little headroom.

   The PR should add an offline test asserting every `LAUNCH` element is at most a margin below the limit (for example 28,000 bytes), and a stub `sandbox create` that enforces 32,768 bytes per element. The PR needs review, and a new run needs a new owner authorization. This record does not implement it.
2. **Cleanup gating.** `done-c0-create` is written before the create call, so cleanup issued `sandbox delete` for a sandbox that never existed. The CLI returned rc=0 with "already deleted". It was harmless here, because the name embeds the run ID. But rc=0 on a missing sandbox could mask a real failure, and the marker does not mean the sandbox exists. A follow-up could gate the delete on a recorded sandbox id or a successful `sandbox get`.
3. The Sonnet pre-run should-notes were not exercised and remain open for that PR's review:
   - the order of the M9 deadline check;
   - the R time budget;
   - no `guard_full` inside the c4a loops;
   - the cleanup marker written before `guard_ctx`.
4. **Phase 2: not justified yet.** Phase 1 as a whole is not tested, and Phase 2 depends on Phase 1 results (`STAGE-C4-PROPOSAL.md`).
