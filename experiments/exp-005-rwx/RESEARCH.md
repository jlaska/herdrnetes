## 1. Provisioning RWX PVCs with the existing `longhorn` StorageClass

- A plain PVC with `accessModes: [ReadWriteMany]`, `volumeMode: Filesystem` against a `driver.longhorn.io` StorageClass is the supported path. Dynamically provisioned volumes take their access mode from the PVC; the volume must be non-migratable (`parameters.migratable: "false"`, the default). [DOCUMENTED] RWX page 1.13.0; SC params page 1.13.0 (`migratable` default `false`).
- `migratable: "true"` requires `volumeMode: Block` + RWX and is meant for VM live migration, not shared filesystems. Not relevant. [DOCUMENTED] SC params 1.13.0.
- `fsType` default `ext4` (also `xfs`); this is the filesystem the share-manager mounts server-side, not what clients see (clients see NFS). [DOCUMENTED] SC params 1.13.0.
- `nfsOptions` (SC param, default `""`) overrides the NFS client mount string for RWX. "You must supply the complete option set; omitted options fall back to NFS **server-side** defaults, not Longhorn's. Longhorn does not validate the string." Test plan must NOT set this (no StorageClass changes). [DOCUMENTED] RWX page 1.13.0.
- Other RWX-related SC params: `shareManagerNodeSelector`, `shareManagerTolerations` (placement of share-manager pod), `allowedTopologies` (-> share-manager affinity). Not needed. [DOCUMENTED] RWX page 1.10.0 (archived; same text family in 1.13.0 not fully re-read).
- **Default NFS mount options.** Source (src v1.13.x, `longhorn-manager/csi/node_server.go`, `nodeStageSharedVolume`): `vers=4.1, noresvport, timeo=600, retrans=5, softerr`; if the kernel rejects `softerr` ("an incorrect mount option was specified") it retries with `soft`. A `sync` option is explicitly commented out ("sync mode is prohibitively expensive on the client"), `hard` is commented out. [DOCUMENTED] source.
  - **Doc/source discrepancy:** the 1.13.0 RWX doc text (as summarised by the fetch tool) says `vers` and `noresvport` "aren't set by default" and only shows them in the example. The v1.13.x source sets both. Treat source as more likely, but **measure** (`/proc/mounts` on the node / `nfsstat -m`).
  - `timeo=600` is tenths of a second (60 s), linear back-off per retrans (source comment). Hard mounts were the default in 1.4.0-1.4.3 and 1.5.0-1.5.1 and could block node shutdown. [DOCUMENTED] RWX page 1.10.0/1.13.0.
  - NFSv4.0 mounts are supported only from Longhorn 1.11.0 (`nfsOptions: vers=4.0,...`). [DOCUMENTED] https://longhorn.io/kb/troubleshooting-rwx-concurrent-writer-process-hang
- Observed real-world mount line (Longhorn 1.2.x era, for shape only): `type nfs4 (rw,relatime,vers=4.1,rsize=1048576,wsize=1048576,namlen=255,soft,noresvport,proto=tcp,timeo=30,retrans=3,sec=sys,...,local_lock=none,...)`. [DOCUMENTED] https://github.com/longhorn/longhorn/issues/3664. Note `local_lock=none` (flock/POSIX locks go to the server).

## 2. share-manager lifecycle

All (src v1.13.x, `longhorn-manager/controller/share_manager_controller.go`) unless noted.

- **Objects created per active RWX volume** (namespace `longhorn-system`, name `share-manager-<pv-name>` for pod, `<pv-name>` for CR/Service/Endpoints/ConfigMap/Lease): ShareManager CR; share-manager Pod (container is `Privileged`); ClusterIP Service (`nfs`/2049/TCP, selector = instance label; headless only when a storage network is configured); a Kubernetes **Endpoints** object (created empty by Longhorn; with a selector Service the endpoints controller fills it; EndpointSlice is mirrored by Kubernetes); a recovery-backend ConfigMap; a `coordination.k8s.io` Lease only if RWX Fast Failover is enabled. Longhorn VolumeAttachment gets a `ShareManagerController` attachment ticket. [DOCUMENTED] source.
- **Where the volume attaches:** the share-manager pod is scheduled to some node, and the Longhorn volume is attached (block device, ext4 mounted) **on that node**, via an attachment ticket Longhorn creates for the pod's node (`createShareManagerAttachmentTicket`). Workload pods mount NFS from the Service ClusterIP (`nfs://<clusterIP>/<volume>`), so workload nodes do **not** attach the block volume. [DOCUMENTED] source.
- **Share-manager only runs while a CSI attacher ticket exists.** When no workload uses the PVC (`isShareManagerRequiredForVolume` false) the controller unmounts, detaches and stops the share-manager pod. The next workload start triggers a cold start (attach, mount, `chmod 0777`, start Ganesha, grace period). So "ordinary workload pod recreation" is invisible to the server **only if at least one other consumer keeps the PVC in use**; if the last consumer leaves, the server restarts. [DOCUMENTED] source. Experiment implication: measure first-mount latency from zero consumers.
- **Server-side start sequence:** wait for device, `mount` (ext4), resize, **`chmod 0777` on the mount root**, create Ganesha export, run `ganesha.nfsd`. Health check does `statfs` and attempts `mount -o remount,rw` if read-only. [DOCUMENTED] source `share_manager.go`.
- **PVC delete with reclaimPolicy Delete:** PV deleted, Longhorn Volume deleted, ShareManager CR (owner of Service/Endpoints) deleted via finalizer path which also deletes the recovery-backend ConfigMap. [DOCUMENTED] source (`syncShareManager` deletion branch + OwnerReferences). Deletion is blocked/stuck if pods still mount it (standard Kubernetes PVC protection) [LIKELY].
- **NFS client node prerequisites:** NFSv4 client (`nfs-common` Debian/Ubuntu, `nfs-utils` RHEL/Fedora, `nfs-client` SUSE); kernel `CONFIG_NFS_V4`, `CONFIG_NFS_V4_1` (RWX needs 4.1). Missing client shows as mount error asking for `/sbin/mount.<type>` helper. Each node hostname must be unique cluster-wide (recovery backend tracks clients by hostname). [DOCUMENTED] https://longhorn.io/docs/1.13.0/deploy/install/#installing-nfsv4-client and RWX page 1.13.0.
- **How Longhorn surfaces missing prerequisites:** Node conditions `RequiredPackages` (NFS client, iSCSI, cryptsetup, dmsetup) and `NFSClientInstalled` (supported client v4.2/4.1/4.0), shown as **warnings** on the Longhorn `Node` resource; they do not block deployment. `longhornctl check preflight` reports "NFS4 is supported" / "Package nfs-common is not installed". `KernelModulesLoaded` lists only `dm_crypt` (and v2 engine modules), **not** `nfs`/`nfsv4`. [DOCUMENTED] https://longhorn.io/docs/1.13.0/nodes-and-volumes/nodes/node-conditions/ and install page. => test plan should read `nodes.longhorn.io` conditions, not assume.
- **Fast failover (experimental):** setting "RWX Volume Fast Failover" (default not stated in the doc page; treat as off/unknown, **read the setting**). When on: Lease object `<volume>` renewed by the share-manager (renew interval 3 s, lease duration 7 s in source); Ganesha `Lease_Lifetime` 20 s and `Grace_Period` 30 s instead of 60 s / 90 s; existing volumes need restart to adopt; known rare deadlock (delete the Lease). [DOCUMENTED] https://longhorn.io/docs/1.13.0/high-availability/rwx-volume-fast-failover/ + source `createShareManagerPod`.
- **Ganesha build in 1.13:** `longhorn/dep-versions` branch v1.13.x pins `rancher/nfs-ganesha` tag **v15.2.0+2** + ntirpc v15.2; branches v1.11.x/v1.12.x pin v9.12.0+1. A custom RecoveryBackend `longhorn` is used. [DOCUMENTED] https://github.com/longhorn/dep-versions (versions.json, v1.13.x). Record the real share-manager image digest and `ganesha.nfsd` version on the cluster.

## 3. NFSv4.1 semantics relevant to git

- **Close-to-open (cto):** client flushes on close and revalidates attributes on open; `nocto` disables (do not use). [DOCUMENTED] nfs(5) https://man7.org/linux/man-pages/man5/nfs.5.html.
- **Attribute cache:** defaults acregmin 3 s, acregmax 60 s, acdirmin 30 s, acdirmax 60 s (unless `actimeo`/`noac`). Directory-entry (LOOKUP) results are cached and dropped when the client sees the directory's mtime change. `lookupcache` unset = revalidate both positive and negative dentries. [DOCUMENTED] nfs(5). Consequence: a pod on node B can see a stale directory listing/attrs for up to 30-60 s after node A creates files **unless** it opens them (cto) or takes a lock (see 5). [LIKELY]
- **Locking is a coherence point:** `do_setlk()` in the kernel flushes writes, then zaps caches after lock acquisition unless a delegation is held. [DOCUMENTED] torvalds/linux v6.12 `fs/nfs/file.c`. Using flock around critical git operations therefore also refreshes the client's view.
- **mtime/ctime:** "The Linux NFS client relies on NFS servers to keep a file's mtime and ctime timestamps properly up to date." All timestamps (index file and worktree files) are assigned by the server's ext4 so cross-node comparisons are internally consistent. [DOCUMENTED] nfs(5); [LIKELY] for consistency.
- **Git racy-index:** git compares st_mtime, st_ctime, st_uid, st_gid, st_ino, st_size (st_dev only with USE_STDEV); entries whose mtime >= index mtime are re-hashed. [DOCUMENTED] https://github.com/git/git/blob/master/Documentation/technical/racy-git.adoc. Risks on NFS: attribute-cache lag between nodes can show stale mtime/size to a second node (spurious "modified" or missed change); uid/gid mapping differences between nodes would make every file look changed. `core.checkStat=minimal` drops sub-second times, uid/gid and inode from the comparison. [DOCUMENTED] git `Documentation/config/core.adoc`.
- **O_EXCL create (git `*.lock`):** git creates lock files with `O_CREAT|O_EXCL` (`lockfile.c`/`tempfile.c`). NFSv4.1 implements exclusive create with a verifier (OPEN EXCLUSIVE4_1, RFC 8881 s18.16) and the Linux client uses it for `O_EXCL`. [LIKELY] (RFC + git source; not tested against Ganesha 15.2).
- **Hard links:** NFSv4 LINK op; Ganesha VFS FSAL passes to ext4. Git loose-object finalisation uses `link()`/`rename()`. [LIKELY] -- measure `ln` across the mount.
- **rename atomicity:** server executes rename as one ext4 op, atomic for other clients. Caveat in rename(2): "On NFS, a failed rename may still have happened" (retransmit after server crash); NFSv4.1 sessions/reply cache reduce but do not remove it. [DOCUMENTED] https://man7.org/linux/man-pages/man2/rename.2.html; [LIKELY] on mitigation.
- **Silly-rename:** renaming/unlinking a file that is still open on the same client creates `.nfsXXXX` files. Relevant if a process holds a file open while promotion/cleanup occurs. [DOCUMENTED] kernel `fs/nfs/dir.c` (`nfs_rename` silly-rename comment, v6.12).

## 4. UID/GID ownership and the UID-1000 stop condition

- **CSIDriver `fsGroupPolicy`:** Longhorn's CSIDriver object (src v1.13.x, `csi/deployment.go` `NewCSIDriverObject`) sets only `PodInfoOnMount: true` and `StorageCapacity`; **`fsGroupPolicy` is not set**, so Kubernetes defaults to `ReadWriteOnceWithFSType`. Longhorn docs confirm: "Because the Longhorn CSI driver csiDriver.spec.fsGroupPolicy is set to ReadWriteOnceWithFSType, the Kubelet attempts to change the ownership and permission" and kubelet proceeds only if the PV's fsType is defined **and the PVC accessModes contains ReadWriteOnce**. [DOCUMENTED] https://longhorn.io/docs/1.13.0/nodes-and-volumes/volumes/pvc-ownership-and-permission/ + source. **Implication:** for an RWX-only PVC kubelet does **not** apply `fsGroup` (no chown/chmod, setting `fsGroup` is a silent no-op). Same result reported for other drivers: https://discuss.kubernetes.io/t/unable-to-set-fsgroup-parameter-in-a-pod-that-uses-rwx-pvc/29375 (a different CSI driver, analogous). Record the actual CSIDriver YAML on the cluster (`fsGroupPolicy` may be set by chart/operator).
- **Initial root owner/mode:** share-manager runs `os.Chmod(mountPath, 0777)` on the ext4 root **every start**; it never chowns, so the root stays `root:root` from mkfs (mode forced to **0777**, no sticky bit). `lost+found` is `root:root 0700`. [DOCUMENTED] src v1.13.x `share_manager.go` L172 + `pkg/volume/volume.go` `SetPermissions` (chmod only).
- **Squash/security flavour:** Ganesha export defaults (src v1.13.x `nfs_server.go`, `export.go`): `Squash = None` (no root squash, no anonymous mapping), `SecType = sys`, `Protocols = 4`, `Access_Type = RW`, `Transports = TCP`, FSAL `VFS`, `NFSV4 { Minor_Versions = 0,1,2; Only_Numeric_Owners = true; Lease_Lifetime = 60; Grace_Period = 90; RecoveryBackend = longhorn }`, `Enable_NLM = false`. [DOCUMENTED] source. With AUTH_SYS and Squash=None, a client UID 1000 acts as UID 1000 on ext4; combined with 0777 root, UID 1000 **can create** entries at the root. Files created are owned `1000:<gid>` (the GID from the pod's credentials; Ganesha with `Manage_Gids` unset uses the AUTH_SYS gid list sent by the client) [LIKELY].
- **Expected answer to the stop-condition question:** UID/GID 1000 non-root can write to the mount root without an init container or fsGroup. [LIKELY] on the 0777 evidence. It was confirmed as intended behaviour by Longhorn issue #2418 (closed 2021, fix = chmod 777 in share-manager, PRs longhorn-share-manager#12 and longhorn-manager#879). https://github.com/longhorn/longhorn/issues/2418
- **Id-mapping:** NFSv4 sends owner strings; Longhorn KB (written for v1.1.0, March 2021) shows `nobody` ownership when the host `/etc/idmapd.conf` `Domain` differs from the share-manager's `localdomain`. https://longhorn.io/kb/troubleshooting-rwx-mount-ownership-set-to-nobody [DOCUMENTED, old]. Current source has `Only_Numeric_Owners = true` on the server; whether the node kernel client uses numeric ids (default for AUTH_SYS when `nfs4_disable_idmapping` is on) is [UNVERIFIED]. Measure `stat -c '%u:%g'` of files created as UID 1000 from two nodes.
- **KNOWN REGRESSION to guard against:** share-manager v1.7.3 (nfs-ganesha v6.x) gave "permission denied" to **non-root** on RWX, specifically **`git clone`** (Longhorn issue #10621 "Error on git checkout in a container", severity/1, hotfix `longhorn-share-manager:v1.7.3-hotfix-1`; upstream nfs-ganesha#1132, still OPEN: "Unable to git clone on top of NFS share with Ganesha v6", `git clone` fails with permission denied, `git pull` works). https://longhorn.io/docs/archives/1.7.3/important-notes/ ; https://github.com/longhorn/longhorn/issues/10621 ; https://github.com/nfs-ganesha/nfs-ganesha/issues/1132. Longhorn 1.13 uses ganesha v15.2.0+2 (a different major line), so status of #1132 on this build is [UNVERIFIED]. **The test plan must include a non-root `git clone` as UID 1000 as an early gate.** Also note #10621's report that setting `fsGroup` did not help, consistent with the fsGroupPolicy finding.

## 5. flock(2) over NFSv4.1

- **Emulation confirmed:** "Since Linux 2.6.12, NFS clients support flock() locks by emulating them as fcntl(2) byte-range locks on the entire file. This means that fcntl(2) and flock() locks do interact with one another over NFS. It also means that in order to place an exclusive lock, the file must be opened for writing." [DOCUMENTED] flock(2) HISTORY https://man7.org/linux/man-pages/man2/flock.2.html. Kernel confirms: `nfs_flock()` comment "We're simulating flock() locks using posix locks on the server" (v6.12 `fs/nfs/file.c`). nfs(5): "Since NFS clients > 2.6.12 implement flock by emulating POSIX locks, this will result in conflicting locks" (with local locks). [DOCUMENTED]
- **Implications:**
  - `flock(LOCK_EX)` on a descriptor opened read-only fails (EBADF) on NFS; open lock files `O_RDWR`/`O_WRONLY|O_CREAT`. [DOCUMENTED] flock(2) wording above; exact errno [UNVERIFIED].
  - Cross-node exclusion works **only if** the mount does not use `nolock`/`local_lock=flock|all`. Default Longhorn mount has no `local_lock` (observed `local_lock=none`). Ganesha has `Enable_NLM=false` so locking uses NFSv4 state, which is fine for vers=4.1. [DOCUMENTED] man 5 nfs; Longhorn issue #3664 mount line; source.
  - Byte-range semantics: locks are per open file description for flock; **POSIX fcntl locks are per process and drop on any close() of the file by that process**. If a process mixes `fcntl` and `flock` on the same file via NFS they conflict (same lock namespace server-side). Python's `fcntl.flock` is fine; `fcntl.lockf` (POSIX) interacts. [DOCUMENTED] flock(2)/nfs(5).
  - Lock acquire acts as a cache-coherency point (flush before, invalidate after). [DOCUMENTED] kernel `do_setlk`.
  - Non-blocking `LOCK_EX|LOCK_NB` returns EWOULDBLOCK on conflict; blocking waits are implemented by client polling/retry in NFSv4 (lock queue not server-side callback unless CB_NOTIFY_LOCK supported) [UNVERIFIED]; test blocking latency.
- **Lease/grace/reclaim after share-manager restart:** after abnormal share-manager termination client I/O blocks until Longhorn recreates the pod; a **90 s grace period** (30 s with fast failover) then lets clients reclaim locks; during grace the server returns `NFS4ERR_GRACE` for READ, WRITE and non-reclaim LOCK; grace ends early if all clients reclaim; **unreclaimed locks are discarded and clients "may see I/O errors"; applications must handle these.** [DOCUMENTED] RWX page 1.13.0. Lease lifetime default 60 s (20 s fast failover). [DOCUMENTED] source `createShareManagerPod`. Recovery backend = dedicated Longhorn service (`longhorn-recovery-backend`); if cluster DNS fails, RWX create/delete/recovery stops. [DOCUMENTED] RWX page 1.13.0.
- **Mutual-exclusion hazard:** after a share-manager restart where a client fails to reclaim in time, a stale holder can believe it still holds a flock while another pod acquires it (lock silently lost; the old holder gets EIO/lock-lost only on next I/O) [LIKELY, from "locks discarded" text]. A lock protecting atomic promotion should be paired with an atomic, idempotent filesystem operation (rename/mkdir) rather than rely on flock alone.
- **Concurrent open hang (known bug):** two or more processes writing/opening the **same file** with NFSv4.1/4.2 can enter D-state indefinitely (`nfs_set_open_stateid_locked`); Longhorn KB workaround is `vers=4.0` (1.11.0+); upstream nfs-ganesha#1327 (closed 2026-06-24, resolution not read; client RHEL9 + ganesha 4.3 reproduces; v4.0 clean overnight). https://longhorn.io/kb/troubleshooting-rwx-concurrent-writer-process-hang ; https://github.com/nfs-ganesha/nfs-ganesha/issues/1327 ; Longhorn #12478 (open, 1.9.2). This matters for lock files opened by many pods and for `index.html`-style append patterns; git itself rarely has many writers on one file. Include a many-process open/lock stress test, with a hard timeout and a note that D-state hangs may require node action (we do not inject failures; just detect/abort).

## 6. renameat2(RENAME_NOREPLACE) over NFS

- **Linux NFS client rejects any rename flag:** `nfs_rename()` begins `if (flags) return -EINVAL;`. Present in v6.12 and master. So `renameat2(..., RENAME_NOREPLACE)` on an NFS mount returns **EINVAL** (no server involvement). [DOCUMENTED] https://github.com/torvalds/linux/blob/v6.12/fs/nfs/dir.c (L2717-2729) and master. rename(2) states the flag "requires support from the underlying filesystem; if not supported, EINVAL." https://man7.org/linux/man-pages/man2/rename.2.html
- **Python:** `os.rename`/`os.replace` call plain `rename(2)` (CPython 3.13 `posixmodule.c` has no `renameat2`). Plain rename of a **file** silently replaces an existing target; of a **directory** onto an existing **empty** directory succeeds (replaces it), onto a **non-empty** directory fails `ENOTEMPTY`/`EEXIST`. [DOCUMENTED] rename(2). To get NOREPLACE you must call `libc.renameat2` via ctypes (glibc >= 2.28) or `syscall(SYS_renameat2)`; both will give EINVAL on NFS.
- **coreutils (util-linux `rename(1)` not examined, [UNVERIFIED]):** coreutils `mv -T --no-clobber` (and `--update=none`) call gnulib `renameatu(..., RENAME_NOREPLACE)`; on `EINVAL/ENOSYS/ENOTSUP` it **falls back to `fstatat()` then `renameat()` and its own comment says "This has a race between the call to fstatat and the calls to renameat"**, i.e. not atomic on NFS. [DOCUMENTED] https://github.com/coreutils/gnulib/blob/master/lib/renameatu.c; coreutils NEWS notes `-n` "is best avoided due to platform differences". So `mv -n` over NFS is a race-prone pre-check, **do not rely on it for exclusivity**.
- **Practical fallbacks** [LIKELY, standard NFS idioms; must be tested]:
  1. `flock` on a lock file + check + `rename()`.
  2. For a **non-empty staging directory**: plain `rename(2)` is already no-replace-in-effect (fails ENOTEMPTY/EEXIST if the target is a non-empty dir), but it **replaces an empty target dir** (so never pre-create an empty `/workspace/<id>` placeholder).
  3. For files: `link(tmp, final)` (fails EEXIST atomically) then `unlink(tmp)`; not usable for directories (EPERM).
  4. `mkdir` as lock (atomic exclusive).
- **Worktree gotcha on promotion:** `git worktree` stores absolute paths in `<worktree>/.git` and `$GIT_DIR/worktrees/<n>/gitdir` by default; renaming a staging dir into place breaks them until `git worktree repair` (or `worktree.useRelativePaths`/`--relative-paths`, which sets `extensions.relativeWorktrees`, git-version-dependent). Missing gitdir paths make worktrees look prunable; `git worktree lock` or `gc.worktreePruneExpire` mitigates. [DOCUMENTED] https://git-scm.com/docs/git-worktree.

## 7. Cross-node simultaneous access

- RWX non-migratable volumes are served by one NFS server pod; any number of pods on any nodes mount the same export concurrently. This is the whole purpose of the feature. [DOCUMENTED] RWX page 1.13.0 ("exposing regular Longhorn volumes through NFSv4 servers"). Contrasts with FIND-063 (RWO: single-node attach).
- Caveats: coherence is "close-to-open", not strict (section 3); one share-manager pod is a single point of failure and a throughput bottleneck for all pods (section 9); the volume's replicas are attached only to the share-manager node. [LIKELY]

## 8. Recovery behaviour (documented only; no failure injection)

- **Share-manager pod terminated / node failure:** client I/O blocks until Longhorn recreates the pod and re-attaches the volume; 90 s grace for lock reclaim; unreclaimed locks discarded -> I/O errors. [DOCUMENTED] RWX page 1.13.0.
- **Without fast failover**, relocation after node failure follows Kubernetes node-failure handling (node NotReady + pod eviction, typically minutes); fast failover can trigger before NotReady (lease 7 s duration in source) and shortens grace to 30 s. [DOCUMENTED] fast-failover page 1.13.0 + source; typical K8s timing [LIKELY].
- **Mount semantics:** default `softerr` (EIO/ETIMEDOUT after retrans exhausted; `timeo=600` = 60 s first try, linear backoff, `retrans=5` => on order of many minutes before an application sees an error) vs `hard` (retries indefinitely; processes hang in D state; "node shutdown may block"). nfs(5): soft/softerr "fails an NFS request after retrans retransmissions"; hard "retried indefinitely". GitLab's NFS doc warns soft "can cause silent data corruption in certain cases" and recommends `hard`. [DOCUMENTED] nfs(5); https://docs.gitlab.com/ee/administration/nfs.html. Longhorn chose soft/softerr "so we can always cleanup mount points" (source comment).
- **Stale handles:** after share-manager restart the same ext4 and fsid (`Filesystem_id = <exportid>.0`, Export_Id reused from config map/recovery state) are re-exported; whether existing client file handles survive a cold restart (volume detached and re-attached, possibly on another node) is [UNVERIFIED]; ESTALE on open files is plausible [LIKELY]. Known open issues: Longhorn #14398 (workload pods not remounted when new share-manager starts same second as remount), #10570 (RWX volume stuck after control-plane upgrade). [DOCUMENTED] issue titles only (not read in depth).
- **Kernel/server-version regression class (important for node choice):** NFS clients on **kernel >= 6.19 / 7.0** against older Ganesha returned `EREMOTEIO` ("Remote I/O error") on readdir/stat/mkdir because the client sends `GET_DIR_DELEGATION` and Ganesha replied `NFS4ERR_OP_ILLEGAL`; fixed in Longhorn 1.11.3+ via Ganesha 9.12 (reported). Distros affected: CoreOS 43.2026-03+, Ubuntu 26.04 (kernel 7.0), Tumbleweed 6.19+, SLES 16 with kernel 7.0.11. Kernel 6.12 / 6.17 unaffected. https://github.com/longhorn/longhorn/issues/13268 ; #13829 ; #14064. Longhorn 1.13 ships Ganesha 15.2.0+2, so this should be fixed but **record node kernel and verify directory listing and `mkdir` immediately after writes on every node.**

## 9. Performance tradeoffs vs ext4 RWO

- Extra network hop (client -> ClusterIP -> share-manager pod) plus userspace NFS-Ganesha (VFS FSAL) on top of the same Longhorn block path that RWO already pays for (iSCSI/engine/replicas). Every metadata op (create, rename, stat after attr-cache expiry) is a synchronous RPC; RWO ext4 serves these from the local page/dentry cache. [LIKELY]
- Longhorn's own docs do not publish an RWX vs RWO benchmark. Evidence found is anecdotal: issue #3664 (Longhorn 1.2.3, baremetal SSD, 1 Gbit): creating 1000 small files took **2m46s on RWX vs "very very fast" on RWO**, tar extraction of git repos at 3-4 files/s; maintainer confirmed no `sync` flag in the mount. Open since 2022 with `area/performance`. https://github.com/longhorn/longhorn/issues/3664 [DOCUMENTED, old version]. Rancher forum thread "RWX-volume is significantly slower than RWO-volume". Longhorn #3037/Aug 2020 report: block-layer overhead is separate. [DOCUMENTED, not re-read].
- GitLab NFS guidance: many-small-file, serialized-write workloads like git are "not well suited" to network/cloud filesystems; Gitaly on NFS is deprecated. https://docs.gitlab.com/ee/administration/nfs.html [DOCUMENTED]. A storage-vendor forum thread cites 9 min (NAS NFS) vs 20 s (iSCSI LUN) for a clone [DOCUMENTED, anecdotal].
- Server is a single pod: CPU/memory limits on the share-manager (check `Guaranteed CPU` setting) bound aggregate throughput. [UNVERIFIED]
- Synchronous server semantics: Ganesha VFS FSAL by default does not export with `sync` and ext4 is mounted normally; durability of client `fsync` depends on COMMIT/stable-write handling. [LIKELY]. Compare `git fsync` cost: `core.fsync`/`core.fsyncMethod` below.
- **Measurement plan:** same small synthetic repos, same pod resources, RWO vs RWX; record wall time for clone, checkout, worktree add, `git status` (hot and after cross-node change), N-parallel clones; client `nfsstat -c` op counts; share-manager CPU. Do not infer from the above numbers.

## 10. Git over NFS: configuration and known issues

All [DOCUMENTED] from git master docs (`Documentation/config/core.adoc`, `index.adoc`, `feature.adoc`, `gc.adoc`) unless noted. Versions of git in the images must be recorded; some options need newer git.

| Setting | Doc statement | Recommendation for this experiment |
|---|---|---|
| `core.preloadIndex` | "especially on filesystems like NFS that have weak caching semantics and thus relatively high IO latencies... Defaults to true." | Leave default (true). |
| `core.fsmonitor` | Built-in daemon "currently available only on ... Windows and MacOS." | Not available on Linux; do not enable hook-based monitors over NFS (they can miss events from other nodes) [LIKELY]. |
| `core.untrackedCache` | "Before setting it to true, you should check that mtime is working properly on your system." Cached via directory mtimes. | Leave `keep`/unset. Directory mtime may be stale across nodes; do NOT enable unless validated [LIKELY]. |
| `feature.manyFiles` | Enables `index.skipHash`, `index.version=4`, `core.untrackedCache=true`. | Avoid on NFS (pulls in untrackedCache). |
| `index.skipHash` | Skips trailing index hash; older clients (<2.13) cannot read, `fsck` older than 2.40 complains. | Optional; safe if git >= 2.40 everywhere. Measure. |
| `core.fsync` / `core.fsyncMethod` | `fsync` (default on Linux), `writeout-only`, `batch` (loose objects only). | Keep default. `writeout-only` weakens durability on a network FS where server crash can lose data [LIKELY]. |
| `core.checkStat` | `minimal` ignores sub-second mtime/ctime, uid/gid and inode. | Consider `minimal` only if spurious "modified" appears; otherwise default. |
| `core.trustctime` | Compare ctime. | Default true; if cross-node attr cache causes false positives, test `false`. |
| `core.sharedRepository` | Not read in detail. | Not needed: same UID 1000 everywhere. |
| `gc.autoDetach` | default true (background gc). | Set false/disable `gc.auto` for experiment to avoid background gc on shared repos. |
| `gc.pid` lock | `builtin/gc.c`: gc.pid holds pid+hostname; same host -> `kill(pid,0)`; **different host -> assumed still running until the file is 12 h old**. Pod hostnames differ, so a crashed pod's gc.pid blocks gc from other pods up to 12 h. [DOCUMENTED] source `builtin/gc.c` `lock_repo_for_gc`. |
| `gc.worktreePruneExpire` | `git gc` prunes `$GIT_DIR/worktrees` entries older than 3 months by default ("never" disables). | Set `never` or lock worktrees. |

- **Lock files:** git ref/index/config locks are `O_CREAT|O_EXCL` temp-file+rename (`lockfile.c`); safe on NFSv4 if exclusive create and rename atomicity hold (section 3). Stale `*.lock` after a pod crash needs manual removal (git does not expire them). [LIKELY]
- **Negative lookup caching:** GitLab's NFS guidance: "Negative cache results cause problems with Git" (e.g. a `git push` may not register uniformly across NFS clients) and recommends `lookupcache=positive` + `hard`; also recommends `vers=4.1` rather than 4.0 and **disabling NFS delegations**. https://docs.gitlab.com/ee/administration/nfs.html. Longhorn default mount leaves `lookupcache` unset (revalidates both) and the plan must not change mount options (no StorageClass changes), so test whether stale negative dentries appear across nodes (node A creates a ref/file, node B immediately stats/reads).
- **Known Longhorn + git issues:** #10621 (git clone permission denied for non-root, ganesha v6, hotfix) [section 4]; #3664 (git bare repos very slow on RWX). No Longhorn doc specifically discusses git. [DOCUMENTED]/[UNVERIFIED] that nothing else exists (search limited).

## Implications for the experiment (what to MEASURE, not assume)

1. **Versions/environment:** Longhorn manager/share-manager image digests, Ganesha version in share-manager (expected v15.2.0+2 on a 1.13 build; 9.12.0+1 on 1.11/1.12), node OS + **kernel version per node** (kernel >= 6.19/7.0 + old Ganesha = EREMOTEIO), nfs-utils/nfs-common versions, CSIDriver YAML (`fsGroupPolicy`), Longhorn setting `rwx-volume-fast-failover`, node conditions `RequiredPackages` / `NFSClientInstalled`, git version.
2. **Actual mount line** on the consuming node: `vers`, `softerr|soft|hard`, `timeo`, `retrans`, `noresvport`, `local_lock`, `rsize/wsize`, `acregmin..acdirmax`, `lookupcache`, delegation state. Reconcile with the doc/source discrepancy on `vers` and `noresvport`.
3. **Stop-condition gate:** as UID/GID 1000 non-root under PSS restricted, with **no fsGroup effect, no chown init container**: `stat -c '%U:%G %a %u:%g'` of the mount root (expected root:root 0777), `mkdir`, create/rename/unlink a file, then **`git clone` of a synthetic repo** (explicit regression check for ganesha issue #1132 / Longhorn #10621). Repeat from a second node and verify `ls -ln` shows numeric 1000 (not `nobody`) on both. Also record that setting `fsGroup` in the pod spec is a no-op.
4. **First-consumer cold start time** (PVC bound -> share-manager running -> first successful mount -> first write), **and** time when a second pod on another node mounts an already-served volume; observe objects: ShareManager CR, pod, Service ClusterIP, Endpoints/EndpointSlice, ConfigMap, Lease (if enabled), attachment ticket node. Observe whether the share-manager stops when the last consumer is deleted (and re-start cost).
5. **flock cross-node:** two pods on different nodes: `LOCK_EX|LOCK_NB` on a file opened `O_RDWR` (one must fail with EWOULDBLOCK), blocking lock hand-off latency, lock on read-only fd (record errno), interplay with `fcntl.lockf`, lock release on pod kill, lock-protected critical-section counter test for lost updates. Use bounded timeouts; do not induce share-manager failure.
6. **RENAME_NOREPLACE errno** via ctypes `renameat2` on the RWX mount (expect EINVAL) vs on the RWO PVC (expect success); behaviour of `mv -T -n` (gnulib fallback, race), plain `os.rename` onto: nonexistent, existing empty dir, existing non-empty dir (expect ENOTEMPTY/EEXIST), existing file; race two nodes promoting the same `<id>`; verify exactly one wins under the chosen protocol (flock + rename, or mkdir-lock). Include `link()`+`unlink()` for files.
7. **Cross-node visibility/coherence:** node A creates a file/dir/ref; measure time until node B sees it via `ls`, `stat`, `open`, `git status`, `git rev-parse`; test negative-dentry staleness (B stats before A creates). Test `git status` stat-cache correctness after A modifies files and B has a warm index (racy-git), with and without lock/`open`.
8. **Git workloads:** clone/fetch/checkout, `git worktree add` with absolute paths, promotion by rename then `git worktree list/repair`, concurrent `git fetch` into one repo from two nodes (lock-file contention), `gc.pid` behaviour (disable auto-gc), hard-link availability (`link()` loose objects) and `.nfsXXXX` silly-rename files.
9. **Performance:** RWO vs RWX wall times and RPC counts for the same workload; share-manager CPU/memory; many-small-file creation (1000 files) as in Longhorn #3664; N parallel pods.
10. **Concurrent-open hang probe:** multi-process open/append stress on one file (bounded duration, watch for D-state) given known issues #11907/#12478/nfs-ganesha#1327; abort and record if hit.
11. **Teardown:** PVC delete with reclaimPolicy Delete: confirm removal of PV, Longhorn volume, ShareManager, Service, Endpoints, ConfigMap, Lease, and absence of lingering NFS mounts / `.nfs*` files.

## Risks

- **R1 Ownership/permissions:** exports are `Squash=None`, root dir 0777; any pod with `runAsUser: 0` (or `CAP_DAC_OVERRIDE` in a non-restricted namespace) is effectively root on the volume. Any pod in any namespace that can bind the PVC reads everything. UID mapping (`nobody`) regressions have occurred (#2357) and Ganesha non-root `git clone` regression (#10621, nfs-ganesha#1132). [DOCUMENTED]
- **R2 Kernel/Ganesha interop:** newer kernels (6.19/7.0) with older Ganesha produced EREMOTEIO on directory ops; any node kernel change can break RWX. [DOCUMENTED]
- **R3 Single share-manager = SPOF + bottleneck;** restart => 90 s (30 s fast failover) grace, I/O stalls, possible lost flock. Fast failover is experimental with documented deadlock edge case. [DOCUMENTED]
- **R4 Locks are best-effort across failures:** unreclaimed locks are discarded; flock cannot be sole mutual exclusion. [DOCUMENTED]
- **R5 NFSv4.1 open-state hang** (D-state) on concurrent opens of one file (#11907, #12478, nfs-ganesha#1327); workaround vers=4.0 needs 1.11.0+ and an `nfsOptions` change (prohibited here). [DOCUMENTED]
- **R6 RENAME_NOREPLACE unsupported** (EINVAL); common tool fallbacks are racy. [DOCUMENTED]
- **R7 Git metadata-heavy performance** penalty (#3664 reported ~100x for small-file creation on an old version); stale dentry/attr caches (3-60 s defaults) can confuse git's stat-cache and ref reads across nodes. [DOCUMENTED]/[LIKELY]
- **R8 Soft mounts (default) can surface EIO/ETIMEDOUT to git mid-write** (potential corruption windows: object files, packed-refs, index.lock); `hard` risks D-state hangs and node-shutdown blocking. Neither can be changed without altering StorageClass. [DOCUMENTED]
- **R9 Prereq drift:** NFS client packages are checked only as warnings; node hostnames must be unique; DNS outages break the recovery backend. [DOCUMENTED]
- **R10 Doc vs source drift:** RWX 1.13 doc text vs v1.13.x source (default `vers`, `noresvport`); results must be based on observed behaviour with recorded digests. [DOCUMENTED]
- **R11 Information gaps:** Ganesha 15.2 exact behaviour for GET_DIR_DELEGATION, status of nfs-ganesha#1132 on this build, fast-failover default, ESTALE behaviour on cold share-manager restart, exact errno for flock on read-only fd: all [UNVERIFIED].
